# Addendum 07 — the home library

Amends [01-foundation.md](01-foundation.md) on game data acquisition and adds one setting.
Everything else stands, including every non-negotiable rule: no game data in the repository, in
releases, or in CI caches; nothing in `host/*` names a game module; the launcher fetches only what a
player asked it to fetch.

## Where this stands against addendum 06

[08-addendum-06.md](08-addendum-06.md) describes `slipgate-server`: a hosted origin at a stable
address, with a public catalogue of freely licensed data and a private per-owner locker, a JSON
manifest at `/catalogue/v1.json`, and a bearer token for the locker. This document does not replace
any of that, and it does not touch the catalogue at all.

What it adds is the case addendum 06 does not cover: an origin that **moves**. A NAS behind a home
tunnel gets a new hostname whenever the tunnel restarts, so no stable base URL exists to configure,
and a beacon is the indirection that fixes it. The library is a locker in every sense that matters —
private, per owner, holding files the owner put there — running on hardware the player already owns
rather than on hosting somebody pays for.

Three deliberate differences, each with its reason, all of which addendum 06 may absorb later:

- **The manifest is tab separated lines, not JSON.** Addendum 06's schema is the client model
  serialised, which is the right shape for a hosted origin with a generator behind it. This one is
  generated by a shell script on a NAS and read by a host with no serialisation library; lines are
  what both ends can do without a dependency. If item 46 lands a JSON manifest client, this library
  should serve that schema too and this format becomes the legacy one.
- **The key travels in the query, not in a header.** `DataDownload.fetch(url, onProgress)` carries
  no headers on any of the three platforms today. Addendum 06's item 47 rewrites that interface for
  resume; a bearer token belongs in the same change rather than ahead of it. The server already
  accepts `Authorization: Bearer` for whichever comes first.
- **`DataSource` is unchanged.** Addendum 06 adds `OwnedOrigin(key)` so a gate can list the origin
  as a route. A library needs no such case: what it offers is discovered from its manifest, so the
  route appears without a gate declaring it. When item 46 adds the case, the library's files should
  be listed through it rather than beside it.

What this shares with addendum 06 is the part that matters most: the inspector stays the authority.
Nothing arriving from a library is trusted because the library said so.

## The gap this closes

Acquisition has two routes. A gate may offer a freely licensed replacement — Freedoom, Blasphemer —
and every gate accepts a file the player supplies from a device they are holding. Neither route
serves the case that actually holds people up: a player who owns the games, keeps them on a NAS, and
plays on four devices. They supply the same file four times, and away from home they cannot supply it
at all.

A third route closes it. The player's own files, served from their own machine, offered to a gate as
one more thing it could install. Not a mirror, not a shared drive, and not a stream: it is the
existing download path pointed somewhere the player owns.

## What it is

**One server, on the NAS, behind a key.** `tooling/library/slipgate-library.py` serves a directory
whose top level is one gate id per directory, `addons` under each for map packs. The layout is the
manifest — there is no index file to keep in step. Three properties are load-bearing rather than
conveniences: a key on every request, because what is being served is commercial game data behind a
public hostname; cross-origin headers, because the web build is a browser and a browser refuses the
request before it is made; `Range`, because a phone on mobile data loses a 700 MB transfer halfway
and a library that cannot resume makes the player start again.

Answering the CORS point from `01-foundation.md`: the web build cannot download either free
replacement, because GitHub's release assets send no `Access-Control-Allow-Origin`. A library run by
the player does send it, so the web build gains a route it never had.

**A tunnel in front of it.** `tooling/library/slipgate-library.sh` boots the server on localhost,
opens `cloudflared` or `ngrok`, reads the public hostname back out of the tunnel's own log, and stays
in the foreground supervising both. The NAS itself never listens on the network.

**A beacon on the site.** A quick tunnel's hostname changes on every restart, which would mean
retyping an address on every device after every power cut. So the script publishes a pointer — where
the library is, and the key — to `site/api/beacon/[id].js`, and the app is configured with the
beacon address instead. That address never changes. The beacon is the first thing in this repository
that is deployed rather than built: `site/` is a Vercel project, and it is skippable, since a player
who only plays at home can configure the library directly.

**One setting.** `SlipgateSettings.libraryAddress`, a single field in Settings → Home library. Which
kind of address it holds is decided by what answers rather than by asking the player to declare it: a
beacon answers with a pointer, a library answers with a manifest.

## What it is not

- Not a mirror and not a share. The key is not optional, the beacon id is a credential, and
  `docs/home-library.md` says plainly that serving commercial IWADs to strangers is redistribution.
- Not a new storage path. A file from the library is inspected, refused or stored exactly like one
  picked by hand, under the entry key the gate looks for. A gate on a train works because every route
  ends in the same shelf.
- Not a new dependency. The server is Python's standard library; the launcher gained no library at
  all, because both documents are tab separated lines under a version header. A serialisation library
  for four fields would be the largest dependency in `host/gamedata`, and a format a `split` can read
  cannot half-parse.

## Decisions worth recording

**The key travels in the query string.** `DataDownload.fetch(url, onProgress)` is one seam over three
platform HTTP clients, none of which carries headers today. A header would mean changing that seam on
Android, the JVM, iOS and wasmJs to serve one caller. The query parameter works on all three
platforms now, travels inside TLS, and its honest cost is a line in the NAS's own log; the server
accepts a bearer token as well, so a future seam change needs no server change. Rotating the key is
restarting the script, which republishes the pointer.

**The pointer is stored under a hash of the id and the publish token.** The id is what every
configured device knows, so using it as the storage path would make the stored document reachable
without going through the function that can refuse the request.

**The library is asked once per session.** `LibraryController` reaches the address as the app opens
and again when it changes, and holds the answer. A player two taps from a gate's data screen should
find the list already there, and a NAS that was off at startup is the ordinary case — hence **Check
again** rather than an error.

## What is left for later

- **Add-ons from the library.** The manifest lists them and `LibraryListing.addOns` returns them; the
  Settings shelf still installs map packs from a file picker only.
- **Add-ons and saves flowing the other way.** A library the app could write to would keep a shelf in
  step across devices. That is a different feature with a different risk profile and is not implied by
  this one.
- **A hash in the manifest.** The server knows each file's size and could publish a checksum, which
  would let the launcher skip a file it already has rather than inspecting it after the transfer.
